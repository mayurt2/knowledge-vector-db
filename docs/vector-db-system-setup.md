# Vector DB System Setup

## Summary
The knowledge search system uses **LanceDB** as its vector database, storing feature documentation as 384-dimensional embeddings generated by the `sentence-transformers/all-MiniLM-L6-v2` model. Each `.md` knowledge file is split into typed chunks, embedded, and stored in a single LanceDB table. A Python `search()` API sits on top for the backend (Java service) to query.

## What this feature does

### Vector Database — LanceDB
- **Database**: LanceDB (local, file-based, no server required)
- **Storage path**: `lancedb_store/knowledge.lance`
- **Table name**: `knowledge`
- **Total rows**: ~1460 chunks from ~103 feature files
- **Index**: Vector index (L2 distance) + full-text search (FTS) index on `chunk_text`

### Embedding Model
- **Model**: `sentence-transformers/all-MiniLM-L6-v2`
- **Embedding dimensions**: 384
- **Normalization**: All vectors are L2-normalized to unit length at ingest and query time
- **Distance metric**: L2 (Euclidean) distance on normalized vectors
- **Similarity formula**: `cosine_similarity = 1 - (L2_distance² / 2)`
- **Score range**: 0.0 (unrelated) to 1.0 (identical)

### Chunking Strategy — 3 chunk types per file

**Type A — Section chunks** (7–8 per file)
Each H2 section of the `.md` file becomes one chunk. Sections merged or split:
- `Summary` + `What this feature does` → merged into one `summary` chunk (always read together)
- `Customer experience` → `customer_experience`
- `Configurability` → `configurability`
- `Which team to connect with` → `contact_team`
- `Related / dependent settings` → `related_settings`
- `Technical reference` → `technical_reference`

All section chunks are prefixed with `[{feature_name} | {category}]` for context.

**Type B — Tags-cloud chunk** (1 per file)
Embeds the feature name + all synonym tags + technical keys as a flat sentence:
`"{feature_name}: {tag1}, {tag2}, ... Category: … Contact: … Technical keys: …"`
Purpose: catches synonym-heavy queries (e.g. "SAP integration" → ERP Sync feature).

**Type C — Sample-question chunks** (6–9 per file)
Each bullet in the `Sample questions` section becomes its own row, enriched with feature context:
`"Q: {question}\n[{feature_name} | {category} | Contact: {contact_team}]"`
Purpose: near-perfect recall when a user's query closely matches a pre-written question.

### Chunk size
- Section chunks: **200–800 tokens** depending on section length
- Tags-cloud chunks: **~50–80 tokens**
- Sample-question chunks: **~30–60 tokens**
- No hard token cap is enforced — sections are kept intact to preserve meaning

## Customer experience
The Java backend service calls the `search()` Python function (or wraps it in an HTTP endpoint). It receives a ranked list of the most semantically relevant chunks for the user's query, ready to inject into an LLM prompt as context.

## Which team to connect with
**👉 Tech Team**

Any changes to the vector DB setup (re-ingestion, model swap, schema changes, new chunk types) are handled by the Tech Team. Knowledge file updates (adding/editing `.md` files) go through the Onboarding Team, who then trigger a sync.

> To re-index after adding knowledge files: run `python3 sync.py --soft` (incremental) or `python3 sync.py --hard` (full rebuild).

## Related / dependent settings
- **Hard Sync** – drops and rebuilds the entire table (`python3 sync.py --hard`)
- **Soft Sync** – re-embeds only changed/new/deleted files (`python3 sync.py --soft`)
- **FTS Index** – full-text index on `chunk_text` used for exact keyword queries (e.g. `noOfApprovers`)
- **Relevance Threshold** – configurable per request; default 0.3 cosine similarity

## Technical reference (for Onboarding/Tech)

### search() API parameters
| Parameter | Type | Default | Description |
|---|---|---|---|
| `query` | str | required | Natural-language question |
| `top_k` | int | 5 | Number of results to return |
| `threshold` | float | None | Min cosine similarity to include (0.0–1.0) |
| `status` | str | None | `"live"` / `"in-development"` / `None` (all) |
| `category` | str | None | Filter by feature category |
| `contact_team` | str | None | Filter by `"Onboarding Team"` or `"Tech Team"` |
| `section_types` | list | None | Filter to specific section types |
| `use_fts` | bool | False | Hybrid vector+FTS for exact keyword lookups |
| `deduplicate` | bool | True | Collapse per-feature, prefer content over Q chunks |
| `route_by_intent` | bool | False | Auto-detect contact/config intent from query |

### search() response — each result dict
```json
{
  "chunk_text":      "The actual content of the chunk (prefixed with [Feature | Category])",
  "feature_name":    "Trip Approval Workflow",
  "feature_id":      "trip-approval-workflow",
  "category":        "Approvals",
  "contact_team":    "Onboarding Team",
  "config_source":   "Policy Config (Corporate Entitlement Service)",
  "status":          "live",
  "section_type":    "summary",
  "section_heading": "Summary",
  "tags":            ["approval", "workflow", "multi-level approval"],
  "score":           0.9544,
  "source_file":     "trip-approval-workflow.md"
}
```

### Score interpretation
| Score range | Interpretation |
|---|---|
| 0.85 – 1.0 | Highly relevant — near-exact match to a sample question or summary |
| 0.60 – 0.84 | Relevant — semantically related, good for answering |
| 0.30 – 0.59 | Possibly relevant — use with caution, review chunk_text |
| 0.00 – 0.29 | Low confidence — topic likely not in knowledge base |
